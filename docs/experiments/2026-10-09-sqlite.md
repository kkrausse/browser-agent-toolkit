# node:sqlite in the guest process (2026-10-09)

Code: `runtime/src/sqlite/`. Decisions: `docs/design/decisions.md`, section "sqlite".

## What was built

- **Engine**: SQLite 3.53.1 (the version native Node 24.18 bundles) compiled from the
  amalgamation with wasi-sdk 34 and `-DSQLITE_OS_OTHER=1`, plus `native/bat_sqlite.c`
  (VFS, in-process locks and WAL index, a few shims). `runtime/src/sqlite/sqlite3.wasm`,
  built by `native/build.sh`. It imports 18 functions from one module (`bat`) and nothing
  else, so `new WebAssembly.Instance` is all the start-up there is.
- **VFS** over an `FsBackend` interface (`backend.ts`): `backend-kernel.ts` (kernel file
  descriptors) and `backend-node.ts` (node:fs, for development).
- **API**: `node-sqlite.ts`, `createSqliteModule(backend, { wasm })` returns the
  `node:sqlite` module object. `builtins.ts` registers it with the process runtime.
- **Harnesses** in `runtime/src/sqlite/harness/`: `compare.mjs` (differential against
  native), `opencode.mjs` (the real server), `bench.mjs`, `crash.mjs`, `browser/` (Chrome,
  real kernel and OPFS).

All timings below were taken on diesel2 (12 cores) while other agents' builds were running;
the load average is given with each set. Under that load single figures move by 2x between
runs, so tables give median and minimum.

## Results in Chrome on the real kernel

Chrome 154, `runtime/src/sqlite/harness/browser/` on port 4105, session `bat-sqlite`: the
page boots the kernel with OPFS persistence, a worker attaches its own kernel instance and
runs the same workloads as `bench.mjs` through `createKernelBackend`. Kernel Wasm:
`target-kernel/…/bat_kernel.wasm` as built at 22:38. Load average 20–31. Five page loads.

| | ms: range over 4 page loads of the median of 5 runs (range of the minimums) |
| --- | --- |
| 6 MB text row insert (one statement, autocommit, WAL) | 35, 43, 45 and, in one load, 154 (minimums 23–52) |
| 6 MB row read, same connection | 7.7–9.7 (6.0–7.4) |
| 6 MB row read after closing and reopening the database | 11.9–15.8 (9.5–11.7) |
| 1,000 small inserts in one transaction | 2.9–6.3 (2.4–2.8) |
| 1,000 small inserts as autocommits | 17.5–24 (9.4–14.8) |
| 1,000 point selects, one prepared statement | 3.1–5.6 (2.0–3.4) |
| 1,000 point selects, `prepare` each time (OpenCode's pattern) | 14.6–20.6 (9.2–15.7) |
| `all()` of 2,000 rows × 4 columns | 2.0–4.0 (1.2–2.2) |
| schema: 60 tables + 120 indexes in one transaction | 13.9–20.8 (11.6–14.1) |
| `WebAssembly.compileStreaming` of sqlite3.wasm (page), five loads | 11–53 |
| instantiate in the worker (`new WebAssembly.Instance` + init) | 0.4–1.3 |

A fifth load ran with `sync: 'wait'` (xSync blocks until OPFS has the data): the 6 MB insert was
129 ms and 1,000 autocommits 76 ms; everything that does not sync was unchanged.

Old runtime, for the same row: 133 ms to read and 272 ms to insert.

**First statements of a process** (open, WAL pragma, 4 pragmas, 20 tables + 20 indexes + 20
inserts in one transaction, one select — the shape of a first boot):

| | ms |
| --- | --- |
| first page load in this browser, no prewarm | 59 |
| later page loads (new kernel, new worker), no prewarm | 10.6, 13.7 |
| after `__bat.prewarm(scratchFile)` in the same worker (prewarm itself 20 ms) | 4.9 |
| second time in the same worker | 6–19 |

V8 compiles Wasm functions lazily on their first call; a first boot goes through about 500
of SQLite's functions including its largest. The later page loads are faster than the first
without anything being done here; whether that is Chrome's code cache for
`compileStreaming` or the renderer keeping the compiled module was not determined.

**Persistence and a tab closed mid-transaction** (`phase=bench` then reload with
`phase=verify`, same OPFS namespace): the worker committed 500 rows and a 6 MB row, awaited
`kernel.flush()`, then opened a second transaction, inserted 3,000 rows with a 10-page cache
so that uncommitted pages were already in the WAL (`keep.db` 6.4 MB, `keep.db-wal` 6.5 MB),
awaited `flush()` again, and the page was navigated away. After the reload kerneld restored
the overlay (snapshot + 1 journal frame, 62 ms) and a new worker opened the database:
`integrity_check` ok, `journal_mode` wal, 500 committed rows, 0 rows of the open
transaction, the 6 MB row intact; after a clean close only `keep.db` remains. One run.

Not covered in the browser: the module registered through `runtime/src/sqlite/builtins.ts`
inside the real process runtime (the check above builds the module directly on a kernel
instance), and OpenCode itself on the kernel. `builtins.ts` typechecks against the
runtime's current `Runtime` type but has not been executed.

## The real consumer: OpenCode 2.0.3

`node --experimental-import-meta-resolve runtime/src/sqlite/harness/opencode.mjs` runs the
27.7 MB bundle through `crates/bat-modules/harness/loader.mjs` with `node:sqlite` replaced
by this module (node:fs backend), twice on one database file; `--native` does the same on
native `node:sqlite`. Both pass: `OPENCODE_SERVER_PROCESS_READY`, `GET /api/health` 200,
exit code 0 after stdin ends, and after each shutdown native SQLite finds the file with
`integrity_check` ok, 20 tables, `journal_mode` wal and no `-wal` left behind. Load 27.

| | calls | Wasm, ms in node:sqlite | native, ms |
| --- | --- | --- | --- |
| first boot, until ready | 186 (1 open, 1 exec, 92 prepare, 92 all) | 52.7 (an earlier run: 82.7) | 5.3 |
| first boot, whole run incl. close | 195 | 62.7 | 9.7 |
| reopen, until ready | 20 (1 open, 1 exec, 9 prepare, 9 all) | 54.0 (earlier: 51.4) | 1.2 |
| reopen, whole run | 29 | 62.4 | 1.9 |

The Wasm figures are the cold cost described above (each run is a new Node process and the
harness does not prewarm): on first boot the single `exec("PRAGMA journal_mode = WAL;")`
took 19–43 ms and `new DatabaseSync` 4–12 ms. File traffic on first boot: 3 opens, 124
writes (252 KB), 5 reads, 4 syncs before ready. The harness environment has no model
catalog, so the 6 MB row is not written here; it is covered by the benchmark rows above.

## API coverage

`harness/compare.mjs` runs 144 cases against native Node 24.18 and this module and diffs
return values and thrown errors (class, `code`, `message`, `errcode`, `errstr`): 0 differ.
It also has each implementation open the other's files (rollback and WAL): 8 of 8 ok.

Covered by those cases: constructor and option checks, `open`/`close`/`isOpen`/
`isTransaction`/`location`/`[Symbol.dispose]`, path as string, Buffer, `file:` URL and URI
filename, `exec`, `prepare`, `all`/`get`/`run`/`iterate` (including Node's iterator
invalidation and restart behaviour), `columns`, `sourceSQL`/`expandedSQL`,
`setReadBigInts`/`setReturnArrays`/`setAllowBareNamedParameters`/
`setAllowUnknownNamedParameters` and the matching database options, positional, `?NNN`,
`$`/`:`/`@` and bare named parameters, every bindable and unbindable value type, integers
beyond 2^53 (ERR_OUT_OF_RANGE, or BigInt with `readBigInts`), constraint errors, foreign
keys, read-only, two connections on one file in WAL and in rollback mode (SQLITE_BUSY as
native), `function` (options, errors thrown from JS, BigInt arguments), `aggregate`
including window functions, `serialize`/`deserialize`, `backup`, `createTagStore`,
`setAuthorizer`, `constants`.

Gaps:

- `createSession`, `applyChangeset`, `loadExtension`, `enableLoadExtension` and the
  `allowExtension` option throw `ERR_FEATURE_UNAVAILABLE_ON_PLATFORM`.
- Not compiled in: FTS3/4/5, R-Tree, Geopoly, DBSTAT, RBU, session/preupdate hook, UTF-16
  API, shared cache. JSON and math functions are in.
- `isOpen`, `isTransaction`, `sourceSQL`, `expandedSQL` are prototype getters; in Node they
  are own accessors of each instance.
- `timeout` sets `busy_timeout`, but the VFS never sleeps (nothing else can run in the
  process while it would), so a busy database fails at once instead of after the timeout.
- `backup` copies in microtask turns rather than on a thread pool.
- `StatementSync` handles of dropped statement objects are finalized by a
  `FinalizationRegistry`, so memory of a prepare-per-query program is returned when V8
  collects, not at a deterministic point.
- No locking between processes: see decisions.

## Durability

`harness/crash.mjs` runs workloads on a logging in-memory backend that declares the kernel
backend's device characteristics, then materializes the files as they stand after every
single file operation and opens them with native SQLite:

| workload | file operations = crash points | xSync calls | bad |
| --- | --- | --- | --- |
| WAL, `synchronous=NORMAL`, autocheckpoint 40 | 1,296 | 19 | 0 |
| WAL, `synchronous=FULL`, autocheckpoint 25 | 948 | 57 | 0 |
| rollback journal (DELETE) | 1,047 | 34 | 0 |
| rollback journal, `synchronous=OFF` | 687 | 0 | 0 |
| control: `journal_mode=MEMORY` (must fail) | 222 | 24 | fails, as it must |

Checked at each point: `integrity_check`, every transaction all-or-nothing, nothing that had
returned from COMMIT missing, rolled-back rows absent. This tests SQLite's behaviour under
the model "a crash leaves every file as of one instant between two operations"; that the
kernel journal actually provides that model was read from `persist.rs` and `kerneld.ts`
(one ordered record stream, taken under the VFS lock, checksummed frames, torn tail
dropped) and exercised once in Chrome (above), not tested exhaustively.
