# The runtime in WebKit (2026-10-11)

Branch `webkit-support`, from `main` at `fb11ec1`. The runtime had only ever run in Chrome.
This is the first pass at WebKit, on diesel2, as a step towards Safari and iOS.

**What "WebKit" means here: Playwright's Linux build (`webkit-2370`, reports WebKit 27.2,
playwright 1.64.0), headless, with a persistent profile. It is not Safari.** Section 7 says
which results should carry over and which may not. Chrome is 154, headed on Xvfb through
`browser-control`, as in the earlier reports. The machine was shared throughout: 1-minute
load 3 to 18, given with the numbers that depend on it.

## 1. Result

- `runtime/harness/check.sh` runs in WebKit (`BAT_HARNESS_BROWSER=webkit`) and passes 12 of
  12 there, and still 12 of 12 in Chrome.
- The TODO example works end to end in WebKit: Open editor, preview visible, chat ready, the
  dark-theme prompt answered by the scripted model, the preview hot-updated in the same
  document, typing and ticking inside the preview. 10 of 10 runs passed, no paid model
  conversation.
- Four runtime changes were needed, none of them large. The exclusive sync access handle,
  which was expected to be the main design problem, was already survivable: the kernel's
  existing fault path covered it.
- Not clean: one WebKit web-process crash and one 60 s hang of `shell.cjs` in 8 full harness
  runs, neither reproduced or explained (section 6).

## 2. How to run it

```sh
bun run setup && (cd examples/todo-app && bun run prepare:editor)
BAT_HARNESS_PORT=4162 BAT_HARNESS_BROWSER=webkit BAT_HARNESS_WEBKIT_PORT=4163 runtime/harness/check.sh
BAT_HARNESS_BROWSER=webkit BAT_HARNESS_WEBKIT_PORT=4163 bun runtime/harness/cli.ts webkit-log    # page console since the last call
BAT_HARNESS_BROWSER=webkit BAT_HARNESS_WEBKIT_PORT=4163 bun runtime/harness/cli.ts webkit-stop   # ends the browser

# the README scenario, with the scripted model instead of a provider
(cd examples/terminal-app && PORT=4165 bun mock-model.ts) &
(cd examples/todo-app && EDITOR_MODEL_API_KEY=not-a-key EDITOR_MODEL_BASE_URL=http://127.0.0.1:4165/v1 PORT=4164 bun run editor) &
(cd examples/todo-app && bun demo/webkit.ts --base http://127.0.0.1:4164 --runs 3)
```

`browser-control` is Chromium-only, so WebKit is driven by the `playwright` package (a root
dev dependency, since `runtime/` is not a workspace member). `runtime/harness/webkit/driver.ts`
keeps one WebKit open and takes the same driver code `cli.ts` gives `browser-control execute`,
so every `cli.ts` command works against either browser. The profile must be persistent: in
an ephemeral context WebKit refuses `createSyncAccessHandle`.

### The exclusive handle

Measured before deciding: WebKit ignores `mode`; a second handle on a file throws
`InvalidStateError` from any worker. The kernel already sends a thread whose host has no
handle to kerneld for the chunk (the path the page always used), so in WebKit every process
read image bodies through kerneld from the first run on. Cost, one process reading 164
files, 25.8 MB, 202 cold 128 KiB chunks: 52.9 ms in WebKit through kerneld, 42.8 ms in
Chrome with its own handle. The chunk cache is shared, so it is paid once per chunk.

The change made that deliberate instead of accidental (no warning into guest stderr, no
race over who opens first) and handled the one place that could not work: the first
download is read while it is written in Chrome; in WebKit the writer's handle is the only
one, so the image is announced when complete. Options considered and why the others lost
are in the decision entry. Chrome's calls are unchanged.

## 7. What should differ on real Safari and iOS

Carries over, because it is WebKit's own code or the specification:

- Exclusive sync access handles and the missing `mode` option; `move` needing the directory.
- A script-set `User-Agent` being sent and preflighted.
- COOP/COEP isolation, shared Wasm memory, nested module workers, Web Locks, the service
  worker serving the preview frame under COEP: all worked here and are long-standing in
  Safari.

May not carry over:

- **The `waitAsync` timeout fault.** It looks like a missing wake-up of the worker's run
  loop, and the run loop is the part that differs between the Linux ports (GLib) and
  Apple's (CoreFoundation). Safari may not have it. The replacement is correct either way.
- **The crash and the hang** of section 3 may be this port's. They may equally be ours.
- **Memory.** The kernel asks for a shared memory with a 4 GiB maximum. It was granted
  here; iOS limits a tab's address space and memory far below a desktop's, and an image
  read in full holds 239 MB in that memory with no eviction. This is the first thing I
  would expect to fail on an iPhone, and nothing here tests it.
- **Storage.** Safari evicts script-written storage of a site not visited for seven days
  and offers no OPFS in Private Browsing; quota prompts differ. Playwright's ephemeral
  context refusing sync handles is Playwright's, not a Safari behaviour to copy.
- **Network stack.** This port uses libsoup; Safari uses the system's. Whether the image
  arrives zstd-encoded, HTTP caching of the runtime files, and request-body streaming
  (`duplex: 'half'` in `sw.ts`, only exercised here with a few bytes of JSON) are all to be
  checked there.
- **Lifecycle.** iOS suspends background tabs and their workers; a suspended kerneld
  holding the only image handle, and the 250 ms journal drain, were not considered.
- **Speed.** Every time above is JavaScriptCore on this x86 Linux machine under load.

## 8. What remains

1. Run it in Safari on the Mac, then on a phone: the harness needs only a served page, but
   `driver.ts` is Playwright; Safari needs `safaridriver` or a manual page.
2. The WebKit web-process crash and the `shell.cjs` hang: no cause. The driver log with
   `DEBUG=pw:browser*` would show WebKit's stderr the next time it crashes.
3. First open in WebKit waits for the whole image. Reading the arriving file through
   `getFile()` + `FileReaderSync` in kerneld would lift that (probed to work while the
   writer holds its handle, 0.6 ms per 64 KiB read); see the decision entry.
4. OpenCode start in WebKit: 1.4–2.4 s from listening to ready after the catalog refresh
   started succeeding. Profile the guest.
5. A second tab on a page that does not persist the overlay (the harness) fails with the
   handle error after a 1 s retry instead of a clear message.
6. Seen in both browsers on this build, base not checked: a guest that does
   `await (await fetch(externalUrl)).arrayBuffer()` and then has nothing left to do did
   not exit in the harness until killed; with `process.exit(0)` it ends.
7. Not tried in WebKit: `examples/terminal-app`, `bench/` (it drives `browser-control`),
   a real or throttled network, large streamed uploads through the preview, session
   export/import, permission cards, Firefox.
