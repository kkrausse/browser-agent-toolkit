# The runtime in WebKit (2026-10-11)

Branch `webkit-support`, from `main` at `fb11ec1`. The runtime had only ever run in Chrome.
This is the first pass at WebKit, on diesel2, as a step towards Safari and iOS.

**What "WebKit" means here: Playwright's Linux build (`webkit-2370`, reports WebKit 27.2,
playwright 1.64.0), headless, with a persistent profile. It is not Safari.** Section 7 says
which results should carry over and which may not. Chrome is 154, headed on Xvfb through
`browser-control`, as in the earlier reports. The machine was shared throughout: 1-minute
load 3 to 18, given with the numbers that depend on it.

## 1. Result

- `runtime/harness/check.sh` runs in WebKit (`BAT_HARNESS_BROWSER=webkit`) and passes 12 of
  12 there, and still 12 of 12 in Chrome.
- The TODO example works end to end in WebKit: Open editor, preview visible, chat ready, the
  dark-theme prompt answered by the scripted model, the preview hot-updated in the same
  document, typing and ticking inside the preview. 10 of 10 runs passed, no paid model
  conversation.
- Four runtime changes were needed, none of them large. The exclusive sync access handle,
  which was expected to be the main design problem, was already survivable: the kernel's
  existing fault path covered it.
- Not clean: one WebKit web-process crash and one 60 s hang of `shell.cjs` in 8 full harness
  runs, neither reproduced or explained (section 6).

## 2. How to run it

```sh
bun run setup && (cd examples/todo-app && bun run prepare:editor)
BAT_HARNESS_PORT=4162 BAT_HARNESS_BROWSER=webkit BAT_HARNESS_WEBKIT_PORT=4163 runtime/harness/check.sh
BAT_HARNESS_BROWSER=webkit BAT_HARNESS_WEBKIT_PORT=4163 bun runtime/harness/cli.ts webkit-log    # page console since the last call
BAT_HARNESS_BROWSER=webkit BAT_HARNESS_WEBKIT_PORT=4163 bun runtime/harness/cli.ts webkit-stop   # ends the browser

# the README scenario, with the scripted model instead of a provider
(cd examples/terminal-app && PORT=4165 bun mock-model.ts) &
(cd examples/todo-app && EDITOR_MODEL_API_KEY=not-a-key EDITOR_MODEL_BASE_URL=http://127.0.0.1:4165/v1 PORT=4164 bun run editor) &
(cd examples/todo-app && bun demo/webkit.ts --base http://127.0.0.1:4164 --runs 3)
```

`browser-control` is Chromium-only, so WebKit is driven by the `playwright` package (a root
dev dependency, since `runtime/` is not a workspace member). `runtime/harness/webkit/driver.ts`
keeps one WebKit open and takes the same driver code `cli.ts` gives `browser-control execute`,
so every `cli.ts` command works against either browser. The profile must be persistent: in
an ephemeral context WebKit refuses `createSyncAccessHandle`.

### The exclusive handle

Measured before deciding: WebKit ignores `mode`; a second handle on a file throws
`InvalidStateError` from any worker. The kernel already sends a thread whose host has no
handle to kerneld for the chunk (the path the page always used), so in WebKit every process
read image bodies through kerneld from the first run on. Cost, one process reading 164
files, 25.8 MB, 202 cold 128 KiB chunks: 52.9 ms in WebKit through kerneld, 42.8 ms in
Chrome with its own handle. The chunk cache is shared, so it is paid once per chunk.

The change made that deliberate instead of accidental (no warning into guest stderr, no
race over who opens first) and handled the one place that could not work: the first
download is read while it is written in Chrome; in WebKit the writer's handle is the only
one, so the image is announced when complete. Options considered and why the others lost
are in the decision entry. Chrome's calls are unchanged.

## 7. What should differ on real Safari and iOS

Carries over, because it is WebKit's own code or the specification:

- Exclusive sync access handles and the missing `mode` option; `move` needing the directory.
- A script-set `User-Agent` being sent and preflighted.
- COOP/COEP isolation, shared Wasm memory, nested module workers, Web Locks, the service
  worker serving the preview frame under COEP: all worked here and are long-standing in
  Safari.

May not carry over:

- **The `waitAsync` timeout fault.** It looks like a missing wake-up of the worker's run
  loop, and the run loop is the part that differs between the Linux ports (GLib) and
  Apple's (CoreFoundation). Safari may not have it. The replacement is correct either way.
- **The crash and the hang** of section 3 may be this port's. They may equally be ours.
- **Memory.** The kernel asks for a shared memory with a 4 GiB maximum. It was granted
  here; iOS limits a tab's address space and memory far below a desktop's, and an image
  read in full holds 239 MB in that memory with no eviction. This is the first thing I
  would expect to fail on an iPhone, and nothing here tests it.
- **Storage.** Safari evicts script-written storage of a site not visited for seven days
  and offers no OPFS in Private Browsing; quota prompts differ. Playwright's ephemeral
  context refusing sync handles is Playwright's, not a Safari behaviour to copy.
- **Network stack.** This port uses libsoup; Safari uses the system's. Whether the image
  arrives zstd-encoded, HTTP caching of the runtime files, and request-body streaming
  (`duplex: 'half'` in `sw.ts`, only exercised here with a few bytes of JSON) are all to be
  checked there.
- **Lifecycle.** iOS suspends background tabs and their workers; a suspended kerneld
  holding the only image handle, and the 250 ms journal drain, were not considered.
- **Speed.** Every time above is JavaScriptCore on this x86 Linux machine under load.

## 9. Reliability follow-up (2026-10-11, second pass)

Same machine, same WebKit build, 1-minute load 3 to 19. Items 2, 5, 6 and part of 7 of
section 8. Every count below is of runs made in this pass.

### 9.1 The web-process crash: a JavaScriptCore fault, made rare, not removed

**Reproduced**: 2 crashes in the first 4 full harness runs (in `shell.cjs`, then in
`semantics.cjs`), with `DEBUG=pw:browser*` and, for the second, WebKit under `strace`
(`BAT_WEBKIT_EXECUTABLE` on the driver). WebKit wrote nothing to stderr either time. What
the browser did was die whole: the web process took SIGSEGV, the others then left with
exit code 0, which is all Playwright reports.

**Cause, confirmed.**

- The signal: `SIGSEGV, SEGV_MAPERR, si_addr=0x10`. The kernel log has the instruction for
  each crash, always the same one: offset `0x1ad7ee1` of `libWPEWebKit-2.0.so.1.12.0`. The
  first report's crash (08:06:24) is in the log too, same offset, on the page's thread; the
  two of this pass were on a `WebCore: Worker` thread.
- That instruction is in `JSC::JSWebAssemblyInstance::updateMatchingCachedMemoriesConcurrently`
  (the library is stripped; identified by the assertion strings of the neighbouring code,
  `SharedArrayBufferContents::tryGrow` just before it and the two `std::span` types it
  indexes, and by its shape against the WebKit source). `tryGrow`, after growing a shared
  memory, walks every instance attached to that memory, in whatever thread, and reads
  `instance->m_memories[i]->memory().shared()`. The fault is the read through a null
  `m_memory`: an instance whose worker was terminated and is being destroyed, whose memory
  object is already gone while the instance is still on the list. (That last clause is
  read from the source, not observed: it is the only way the pointer is null there.)
- Without any of the runtime: `runtime/harness/webkit/grow-crash/` is one worker growing a
  shared `WebAssembly.Memory` a page at a time while other workers instantiate a module
  that imports it and are terminated. **4 of 4 runs crash within 1.3 s, at the same
  instruction. With the grow left out: 8,644 terminations, no crash.**

The kernel grew its memory 1 MiB at a time: 84 grows in `spawn`, `shell`, `semantics` and
`typescript` alone, most of them while process workers were being terminated.

**Fix** (`7f8bf72`, comment corrected in the commit of this section): the kernel heap grows
64 MiB at a time (`crates/bat-kernel/src/alloc.rs`); the same four scripts now grow it
twice. A 64 MiB grow took 1.6 ms in WebKit and 3.7 ms in Chrome, and the web process was
no larger (303 → 314 MiB after boot, 666 → 668 MiB after the four scripts; one process
reused, so indicative only).

**After it: 82 full harness runs in WebKit, no crash** (984 scripts; one run lost a script
to my stopping its file server by mistake, not counted against it).

This lowers the odds by the number of grows; it does not remove the fault. A session that
fills the image cache still grows a handful of times, and each grow that meets a worker
being destroyed can kill the tab. I found nothing a page can do to order another thread's
teardown against a grow: there is no event for "that worker's heap is gone". Whether
Safari has it is not known: the code is not port-specific (JavaScriptCore), the function
exists on WebKit `main` today, and the instance list it walks came in September 2025
(`WasmInstanceAnchor`, bug 299024), so Safari 18 should not have it and current Safari
may. The grow-crash page is the test: serve the directory, open it, `go(20, 'race')`.

### 9.3 A guest that ends on a `fetch` did not exit (item 6)

**Reproduced** in Chrome and WebKit, and **on `main` before this branch** (`fb11ec1`'s
runtime built aside and run in Chrome): `await (await fetch(url)).arrayBuffer()`, and
plain `await fetch(url)`, sat until killed. It is not about `arrayBuffer`.

**Cause**: the loop decides whether a process is finished at the end of a turn, and a
turn starts from a timer, a kernel event or a ping. `fetch.ts` holds the process with
`loop.ref()` and releases it with `loop.unref()` when the browser's promise settles, which
is a browser task of its own, not a turn; `unref()` only decremented. The same for a
`clearTimeout()` there: `const t = setTimeout(f, 6000); await fetch(u); clearTimeout(t)`
lived the whole 6.0 s.

**Fix** (`b0b5c6a`, `runtime/src/process/loop.ts`): dropping a reference outside a turn
asks for a turn when the count reaches zero. Run in both browsers: the two fetch cases
exit in 14–91 ms, the timer case in 17–23 ms, a body read 300 ms after its response still
gets `beforeExit`. No regression test: the one I tried in `semantics.cjs` passed on the
unfixed runtime too, so it was not kept.

### 9.4 A second tab on a page that does not persist (item 5)

**Fix** (`fe3b17b`): the keeper's give-up in `openImage` (`runtime/src/kernel/opfs.ts`, one
branch, nothing else in the file) throws code `EBUSY` with "This workspace is already open
in another tab or window, and this browser lets only one of them read its files. Close it
there, then reload." instead of WebKit's `InvalidStateError`. Run: second harness tab in
WebKit, the message after 1.3 s (the retry is unchanged) and the first tab still runs
guests; in Chrome a second tab boots as before.

### 9.5 `examples/terminal-app` in WebKit (item 7)

**It did not start**: the OpenCode server exited with code 1 at its first
`importScripts`. That example ships its big files only as `.gz` and its service worker
inflates them, so a request that misses the service worker gets a 404, and two of the
process workers were not controlled by it.

**Cause, measured**: each worker reported `navigator.serviceWorker.controller` over a
`BroadcastChannel`. kerneld is controlled; of the three process workers it creates at
start-up from one URL, one is controlled and two have `controller === null`, and those two
are the 404s. Playwright sees one response for the worker script at that point, not three:
the loads are shared, and only the worker whose load reached the service worker gets a
controller. Workers created later, singly, are controlled. The TODO example hid this
because its server has the files under their own names (whether its workers are
uncontrolled too was not measured).

**Fix** (`ea42de5`): a worker told that its creator is controlled says so if it is not,
before it attaches to the kernel; kerneld replaces it and from then on gives each process
worker a URL of its own (`?worker=N`), so no two loads are shared. Chrome never reports
one, so its URLs and its code cache are as before. The cost in WebKit is the two warm
workers thrown away at start-up.

`examples/terminal-app/demo/run.ts --webkit` runs the scenario's own steps in Playwright's
WebKit. Scripted model: **4 of 4 in WebKit** (open 3.5–3.9 s, reply 15.6–16.2 s), 1 of 1
in Chrome after the change. One console error in WebKit, not looked into: a cross-origin
redirect refused for `tree-sitter-css.wasm` from GitHub's release host (the run had
`tunnel=0`).

### 9.6 New: in the TODO scenario the second hot update sometimes never shows

Found while checking the fixes against `examples/todo-app/demo/webkit.ts`: **19 of 116
runs failed** at "expected 1 left", always the same way. The agent's edits are all
`completed`; the preview is dark and is the same document; the dev server, asked again,
serves `home.tsx` with both edits; but the document has loaded one hot update of
`home.tsx`, not two, and shows neither the count nor an error for 10 s. So the second
update never reached the page, or was not acted on.

It is not from this pass's changes, as far as 116 runs can say: 16 of 76 with the 64 MiB
step, 3 of 40 with the old 1 MiB step, and in the two batches run back to back 3 of 15
against 2 of 15; 1 of 6 with the loop fix taken out, 1 of 8 with the worker replacement
taken out. I did not run the exact commit of the first report, whose 10 of 10 this
contradicts, and not Chrome (the scripted scenario is WebKit-only). Not explained. The
scenario now records `preview` and `served` on a failure.

31 GiB tmpfs, where the scenario puts its profiles) was at 80% and moving by gigabytes;
it did not recur once I had deleted my profiles. Taken as the machine, not verified.
