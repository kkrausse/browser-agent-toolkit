# Guest tools: esbuild, dependency optimizer, Tailwind scanner, lightningcss, rollup, Babel (2026-10-09)

What replaces the generic WebAssembly builds of the native tools in the Vite guest, what it
costs, and how each replacement was checked. Decisions: `docs/design/decisions.md` (entries
dated 2026-10-09 "tools"). Everything here was measured with **native Node 24.18** and, for
esbuild, in **Chrome 154**; nothing was run on the new browser runtime, which did not exist
yet.

Machine: diesel2, 12 cores, other agents compiling throughout. The load average is given
beside every set of timings; treat absolute numbers as upper bounds and compare within a
row or table (runs are interleaved).

## How things were measured and compared

All scripts are in `crates/bat-tools/harness/`.

- **Trees.** `bat-prepare deps` with a policy gives a guest `node_modules`; with the app's
  sources beside it that is a runnable copy of the guest's `/workspace`. Three policies:
  no substitutions (`native`: real esbuild, rollup, lightningcss, oxide), the old table
  (`old`: `esbuild-wasm`, `@rollup/wasm-node`, `lightningcss-wasm`,
  `@tailwindcss/oxide-wasm32-wasi`), and the current table (`shims`).
- **`vite-crawl.mjs`** mounts a tree at `/workspace` in a mount namespace (bubblewrap),
  starts Vite exactly as the guest's launch description does (`vite --configLoader native
  …`, `BROWSER_AGENT_GUEST=1`, `NODE_ENV=development`), then requests what a browser
  requests for the first page: the document and, transitively, every module it imports
  (31 requests). It reports spawn → listening, the document, and spawn → last module.
  Two of the 31 are 404s in every tree (import-looking strings inside React's comments).
- **`esbuild-trace.cjs`** records every esbuild API call of a run with its input, options
  and result; `replay-esbuild.mjs` replays such a recording through the shim and compares.
- **`bench-crawl.mjs`**, **`bench-esbuild.mjs`**, **`bench-wasm.mjs`**: interleaved runs,
  fresh process each.

### The shim

`crates/bat-tools/src/esbuild.rs` (transform, oxc 0.153) → `crates/bat-tools/wasm`
(cdylib, plain C ABI, no imports, built by `crates/bat-tools/build-wasm.sh`) →
`packages/guest-shims/esbuild/lib/` (`bat-main.js` the API, `bat-oxc.js` the binding,
`bat_esbuild.wasm`). Prepare lays these over the installed `esbuild-wasm` and sets its
`main` (`package.overlay.json`).

Environment needs: `WebAssembly` and `fs.readFileSync`, or a precompiled module from
`globalThis.__bat_wasm('esbuild')` (then no `fs`). `BAT_ESBUILD_SHIM_LOG=<file>` logs which
path served each call.

| esbuild option | What the shim does |
| --- | --- |
| `loader` `js` `jsx` `ts` `tsx` | oxc; `js`/`jsx` parsed as module or script by content |
| `sourcemap` `true`/`external`/`inline`/`both`, `sourcefile`, `sourcesContent`, `sourceRoot` | version 3 map from oxc's printer, one source |
| `jsx`, `jsxDev`, `jsxFactory`, `jsxFragment`, `jsxImportSource` | oxc JSX transform; the options win over `tsconfigRaw`, as in esbuild |
| `tsconfigRaw` (object or JSONC string) | `jsx*`, `verbatimModuleSyntax`/`preserveValueImports` (unused imports kept), `useDefineForClassFields` with esbuild's default rule from `target`, `experimentalDecorators` |
| `define` | oxc's global-define replacement (identifiers, member chains, `import.meta.*`) |
| `minifyWhitespace` | oxc's printer without whitespace |
| `charset`, `legalComments` `none`/`inline` | printer options |
| `target`, `supported`, `platform`, `keepNames`, `treeShaking`, `ignoreAnnotations`, log options | accepted, no effect: **nothing is ever downlevelled**, renamed or removed |
| `minify`, `minifyIdentifiers`, `minifySyntax`, `mangle*`, `drop*`, `pure`, `banner`, `footer`, `globalName`, `format` `cjs`/`iife`, other loaders (`css`, `json`, …), any unknown option | real esbuild |
| input with decorators (either kind), `import x = require()`, or needing an oxc runtime helper | real esbuild (oxc would import `@oxc-project/runtime`; esbuild inlines) |

So minification is whitespace-only natively and real minification is exact but slow
(first use starts `esbuild-wasm`): nothing in dev mode asks for it. `build()` handles one
entry whose imports all become external (plugins' `onResolve`, Node builtins on
`platform: node`), reading the nearest `tsconfig.json` as esbuild does; `context()`,
`buildSync`, `analyzeMetafile` are the real esbuild; `formatMessages` is plain JS.

Result and error shapes follow esbuild: `{ code, map, warnings, mangleCache, legalComments }`;
failures throw `Error("Transform failed with 1 error:\n<file>:<line>:<col>: ERROR: <text>")`
with `errors[]`/`warnings[]` (`location.line`, UTF-16 `column`, `length`, `lineText`).
The message **text** is oxc's (`Unexpected token` where esbuild says `Unexpected ";"`).

### Evidence that behaviour matches

1. **Replay of the recorded calls**: `replay-esbuild.mjs out-native/esbuild-trace.jsonl
   <shim tree>`: 21 of 21 transforms produce the same syntax tree as real esbuild's
   recorded output; 21 of 21 source maps are version 3 with the same `sources` and
   `sourcesContent`. Trees are compared with Babel's parser, ignoring positions and
   comments, after undoing printer differences that do not change meaning (each is
   listed at the top of the script): oxc aliases the JSX runtime import
   (`jsxDEV as _jsxDEV`), names the file once (`var _jsxFileName`), orders that import
   differently; esbuild prints `undefined` as `void 0`, folds `"a" !== "b"` and `"a" + "b"`
   after `define`, suffixes shadowing bindings (`value2`), prints substitution-free
   templates as strings, and emits `export {}` for a module left empty.
2. **A wider corpus** (`corpus-trace.mjs`): 123 TypeScript/TSX/JS files of this repository
   (toolkit UI, runtime, example, loader fixtures) × 3 option sets (Vite's dev options;
   `react-jsx` with `useDefineForClassFields: false`; classic JSX with a factory, `target:
   ES2020` and `define`) = 369 transforms: **354 the same, 15 differ**, 369 maps
   accepted. The 15 were read by hand and are four output shapes with the same meaning:
   class fields lowered to constructor assignments under `useDefineForClassFields: false`
   (`constructor(..._args)` where esbuild writes `...arguments`, differently named
   temporaries for computed keys; 8, in four files), a parameter property's field declared
   before rather than after the constructor (1), a TypeScript `enum` wrapped in a function
   rather than an arrow (3), and top-level `this` in a module kept where esbuild writes
   `void 0` (3). The field-lowering outputs were read, not executed.
3. **The dev server**: with the shim tree, Vite starts, serves all 31 requests with the
   same statuses as the native tree, and every esbuild call is served by oxc (22 calls, 0
   fallbacks; with a hot update 25, 0). `style.css` is byte-identical. The app's own
   modules differ textually from the native tree (oxc's printer, then React Router's Babel
   pass); they were not compared byte for byte.
4. **Chrome**: the shim-backed dev server's page renders (`h1` "Todos", form present,
   stylesheet applied, React hydrated from the shipped optimizer cache, HMR socket
   connected; the only errors are the missing favicon and `/api`, which had no backend in
   this check). Editing `src/home.tsx` updated the heading without a reload.
5. **The reference loader** (`crates/bat-modules/harness/run.mjs --app <shim tree>`): all
   13 scenarios pass, including "vite dev server: listens and serves a transformed TSX
   module", i.e. the shim loads and runs under the new module format.
6. Fallback paths, natively: a CSS `transform` with `minify` and a decorator input go to
   `esbuild-wasm` and return its output (893 ms for the first such call); the optimizer
   runs through `context()` when no cache is shipped.

Not checked: `transformSync` falling back (it needs `esbuild-wasm`'s synchronous service:
`child_process.execFileSync` of `node`, or worker threads); error message texts beyond one
case; `importsNotUsedAsValues`.

## 2. Dependency optimizer cache from prepare

### What Vite checks

`loadCachedDepOptimizationMetadata` (Vite 7.3.6) reads `<cacheDir>/deps/_metadata.json`
and accepts it when two hashes match:

- `lockfileHash`: sha256 of the first lockfile found walking **up from the root**
  (`bun.lock`, `node_modules/.package-lock.json`, …, plus the mtime of a `patches`
  directory). The TODO guest has none in or above `/workspace` (the app is a workspace
  member, so prepare ships no lock): the hash is that of the empty string, `e3b0c442`.
- `configHash`: `NODE_ENV`/mode, **`root`**, `resolve`, `assetsInclude`, plugin **names**,
  `optimizeDeps.include`/`exclude`/`esbuildOptions`.

Nothing else is validated at load. `hash` is derived from the two; `browserHash` becomes
the `?v=` query; each dependency's `fileHash` covers `hash`, the **absolute** output path
and the chunk's imports, and is compared only between two optimizer runs. Paths inside
`_metadata.json` and inside the bundles are relative, so the files themselves relocate.
The cache directory is the toolkit plugin's `.browser-editor-cache/vite` under the root.

### How it is produced

`packages/guest-shims/prepare/vite-optimize-deps.mjs`, run by prepare as a policy
`projectScripts` entry when the tree has `vite`:

1. The project files prepare will deliver (`BAT_PROJECT_FILES`) are written beside the
   guest `node_modules` (`<work>/guest/`), giving the guest's `/workspace` layout.
2. With bubblewrap, that directory is bound at `/workspace` in a mount namespace and
   `vite-optimize-runner.mjs` starts the project's own Vite there through its API with the
   guest's launch environment (`createServer({ configLoader: 'native' })`, loopback,
   port 0), waits for the optimizer, then requests the first page's module graph so that
   dependencies Vite would only discover in the browser are optimized too, waits again,
   and closes. Vite writes the cache; the script only copies `<cacheDir>/deps*` out.
   Because the process really runs at `/workspace`, every hash is the guest's own.
3. Without bubblewrap (macOS), Vite runs at the host path and the runner rewrites
   `configHash`, `lockfileHash` and `hash` for the guest root with a copy of Vite's two
   functions, after checking that the copy reproduces the hashes Vite itself just wrote
   for the host root (otherwise the script fails and nothing is shipped). `fileHash`
   values then still contain the host path: the first re-optimization in the guest may
   reload the page where it would not have. No page walk in this mode (Tailwind would
   scan whatever surrounds the stage directory).
4. Output files become project files (`/.browser-editor-cache/vite/deps/*`), plus
   `/.browser-editor-cache/vite/.gitignore` (`*`), see §3.

The optimizer itself runs through the tree's own `esbuild`, i.e. the shim's fallback to
`esbuild-wasm`: the bytes are what the guest would have produced.

Results are cached by project files + image hash + launch environment; an unchanged
prepare run takes 0.11 s in total. A change to any project file reruns the script
(6–11 s under this load, of which the optimizer in `esbuild-wasm` is 3–5 s).

### Result

- TODO app: 11 dependencies, 7 chunks, 39 files, 5.81 MB (2.1 MB of JS, 3.7 MB of source
  maps). No `deps_ssr`: this app has no SSR optimizer.
- Both modes give the same `hash 034fee99`, `configHash 82758302`, `lockfileHash
  e3b0c442`, equal to what Vite wrote on its own in a `/workspace` run of the same tree.
  Two bundles differed between two runs only in the order of two import statements
  (esbuild's chunk import order is not stable between runs).
- Accepted by the guest's Vite: started on a tree holding the shipped cache, Vite logs no
  re-optimization, the cache files are byte-identical afterwards, the page's dependency
  URLs carry the shipped `browserHash`, and `esbuild-wasm` is never loaded (0 `context`
  calls in the shim log).
- `manifest.json` grows from 24 KB to 6.0 MB.

### What the fallback costs

Without a shipped cache the guest runs the optimizer in `esbuild-wasm`, started when the
optimizer first asks for it. In the table of §7 that is the "shims, no cache" row: 2163 ms
to the first page against 894 ms with the cache (about 1.3 s more), and still 0.3 s less
than the old tree's fresh open, whose transforms also went through `esbuild-wasm`. An
agent-installed dependency takes this path once.

### Caveats for the runtime and prepare owners

- **Stale caches.** Vite's only knowledge of the dependency tree is the lockfile hash, and
  this guest has no lockfile, so a cache left in a persisted workspace from an older
  deployment is accepted even if dependency versions changed. The shipped cache must
  **replace** an existing one when the prepared output changes ("source install preserves
  existing files" must not apply to it), or prepare should also deliver the lock text for
  workspace-member apps so that Vite notices by itself.
- **Renaming the directory.** A re-optimization (an agent installs a dependency) renames
  `deps` away and a temporary directory into place: the cache has to live in the
  writable overlay. That, and the manifest size, are why it is in project files.
- The stage run executes the project's Vite config and renders the document once on the
  build host, as `vite build` would.

## 3. `@tailwindcss/oxide`

Package `packages/guest-shims/tailwindcss-oxide` (`dir:` substitution for
`@tailwindcss/oxide`; no dependencies; the `wasm32-wasi` N-API package and its emnapi
runtime are no longer installed). Crate `crates/bat-tools/oxide` (own workspace,
`build-wasm.sh`).

- **Surface** (from `@tailwindcss/node` and `@tailwindcss/vite` 4.3.3): `new Scanner({
  sources })`, `scan()`, `scanFiles()`, `getCandidatesWithPositions()`, getters `files`,
  `globs`, `normalizedSources`, and `scannedFiles` (the Vite plugin uses it).
- **Target `wasm32-wasip1`** with a synchronous WASI preview1 in the package (`wasi.js`,
  19 imports, read-only, one preopen `/`) over `readFileSync`, `readdirSync({
  withFileTypes })`, `statSync`, `lstatSync`, `readlinkSync`. The scanner, its vendored
  `ignore` walker, `walkdir`, `globwalk` and `dunce` all use `std::fs`; on
  `wasm32-unknown-unknown` four crates would need their file access rewritten. Rayon needs
  nothing: without threads its pool runs on the caller. The module comes from
  `globalThis.__bat_wasm('tailwindcss-oxide')` when that returns one.
- **Source: tag v4.3.3, vendored, not the fork rev.** `kkrausse/tailwindcss@11050dda` is
  upstream `main` plus one line, and that `main` is well past v4.3.3 (`crates/` differs
  by 27 files); built from it the scanner showed 283 differences against the native 4.3.3
  binding on a symlinked source. `vendor/tailwindcss-oxide` is `crates/oxide/src` at
  c2b24dd (MIT notice kept) with the fork's one-line change applied (no parallel walker
  on re-scan).
- **`same-file` is stubbed** (`[patch.crates-io]`): the published crate errors on WASI,
  which makes the walker drop every symlinked directory (a source pointing into Bun's
  `node_modules/<pkg>` scanned 220 candidates instead of 1,341).

'/workspace', pattern: '**/*' }`: 61 files, 5.83 MB, 7,657 candidates; medians):

- `crates/bat-tools/oxide/harness/compare.mjs` against the native 4.3.3 binding, at
  `/workspace` and in place: **identical** for the traced source set and three others
  (globs with negation and a symlinked package, a relative base, no sources): `scan()`
  twice, `files`, `scannedFiles`, `globs`, `normalizedSources`, `scanFiles` and

**Finding: the scanner was walking Vite's dependency cache.** `/workspace` has no
`.gitignore`, the stylesheet has no `source()`, so Tailwind's automatic source is the
whole root, and 38 of the 61 scanned files (5.81 of 5.83 MB) were
`.browser-editor-cache/vite/deps/*`. Every utility class in the 11,310-byte `style.css`
came from React's and React Router's bundles, and the output depended on timing: a scan
that ran before the optimizer had written its files produced 6,146 bytes (seen once in
19 runs with the shim, the remaining one). The optimizer script now ships
`.browser-editor-cache/vite/.gitignore` containing `*`: the scanner (native or shim)
then reads the 14 source files and `style.css` is always the 6,146-byte result. **This
changes the served CSS on purpose**; removing the three lines in `vite-optimize-deps.mjs`
restores the old behaviour. A `.gitignore` among the project's own files would do the
same.

Share of a `style.css` transform (native binding, one crawl, load 11–12; 4 transforms, 2
`new Scanner`, 4 `scan()`): 270 ms (scanner 121), 288 (111), 57 (30), 37 (28). The rest is
Tailwind's JS: `import('@tailwindcss/node')` 135 ms once, `compile()` 87 ms then 48 and
20. lightningcss is not called.

Not checked: the browser runtime's `fs` (`Dirent` types, `mtimeMs` for change detection,
`readlinkSync` errors), `FinalizationRegistry` there; edits between scans against native;
template pre-processors (no such files in the app); Windows paths.

Shim: `packages/guest-shims/lightningcss` (overlay on `lightningcss-wasm`): `bat-main.cjs`
/ `bat-main.mjs` (entries), `bat-load.cjs` (its own loader: the package's entries all
instantiate at load and locate the file through `import.meta.url` or `require('url')`),
`bat-vendor/` (`Features`, `browserslistToTargets`, `composeVisitors` from native
lightningcss 1.32.0, MPL-2.0 notice kept; they never load the Wasm). Needs `WebAssembly`
(a synchronous compile of 15.9 MB when it does load, so a worker), `fs`, `path`,
`crypto.getRandomValues`, `TextDecoder`, `FinalizationRegistry` (napi-wasm).

Evidence: installed through prepare's overlay; output identical to native lightningcss for
`transform` with the exact options of Tailwind's `optimize()` (also with `minify` and a
source map), composed visitors, `transformStyleAttribute`, `bundle`, `bundleAsync` with an
async resolver; 5 of 8 interleaved crawl pairs with/without the shim identical in all 31
bodies after replacing per-start values, the other 3 differing only in the optimizer's
bundles (import order: 24 of 56 same-tree pairs differ the same way, see §2). The startup
difference from this shim alone is inside the run-to-run noise of that session (paired
median +148 ms to listening, range −525 to +479); the load cost above is the dependable
figure.

## 5. rollup

`@rollup/wasm-node@4.64.3`: `bindings_wasm_bg.wasm` 581,963 bytes, loaded synchronously

for everything after.

For a later agent:

- **One call is avoidable today.** React Router skips ids containing `/node_modules/`
  for the refresh pass, but the toolkit's `cacheDir` is `.browser-editor-cache/vite`, so
  the optimized `react_jsx-dev-runtime.js` is run through Babel (the most expensive single
  call, 122 ms) although it needs no refresh wrapper. A cache directory whose path
  contains `/node_modules/` (inside the writable overlay) would skip it.
- **Precomputable** for unedited files: the route transforms (both passes) and the
  refresh passes. A cache key must cover the hash of the code the transform receives (it
  is esbuild's output, now the shim's, not the source file), the module id (it is written
  into the source map), the `ssr` flag, the React Router config (`ssr`, `future`), and
  the versions of `@react-router/dev`, `@babel/*`, `babel-dead-code-elimination`,
  `react-refresh`. The critical-CSS parse depends on the current Tailwind output and is
  not precomputable. Loading Babel (170 ms) is paid regardless unless React Router's
  requires become lazy.

Where the time of a native start goes (one CPU profile, 1594 ms active, to first page;
load 22): Node internals other than loading 360 ms, Vite 292, Babel 258, module loading
225, Tailwind's JS 170, React Router/React 74, GC 65. In the old tree the Vite thread
additionally spent 208 ms in the oxide Wasm, 50 in lightningcss, 47 in rollup, and idled
1.7 s waiting for the `esbuild-wasm` child process, which used 2.7 s of CPU (84% Go Wasm).
The old tree is three threads of execution (Vite, the esbuild child, an oxide worker);
the shim tree loads neither of the packages that start the other two (thread count not
measured directly).

## What still falls back to a generic Wasm package

- `esbuild-wasm`: the optimizer when a new dependency appears (or no cache was shipped);
  `build()` of a config that imports local files; real minification, `format: cjs|iife`,
  CSS and other non-JS loaders, decorators, `import x = require()`. It needs a child
  `node` process (or worker threads for the synchronous API), as before.
- `lightningcss-wasm`: only when something calls it (a build; `css.transformer:
  'lightningcss'`).
- `@rollup/wasm-node`: unchanged, always.

## Not verified

- Anything on the browser runtime: all of this ran under native Node 24 (and the esbuild
  transform in Chrome workers). In particular the shims' `fs` use, the
  `globalThis.__bat_wasm(name)` hook from a real runtime (it was exercised from a test
  harness for `esbuild` and `tailwindcss-oxide`), synchronous compilation of the Wasm
  files inside a guest process, and the fallback's child process.
- The host-path mode of the optimizer script on macOS (it was run on Linux with
  `BAT_NO_BWRAP=1`).
- How the runtime installs project files over an existing workspace (see §2 caveats),
  and a 6 MB manifest's effect on open time.
- Tailwind re-scans after edits against the native scanner; the hot-update path was
  checked once in Chrome (one edit of `home.tsx`).
- One `bat-prepare deps` run failed with Bun's `EEXIST: failed to link package:
  @tailwindcss/oxide@.bat-shims/_tailwindcss_oxide` and succeeded when repeated; not
  investigated.
