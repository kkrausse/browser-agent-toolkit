# Startup: measured budgets, what changed, what is left (2026-10-10)

Branch `rewrite/rust`, commit `f01d11c`. The TODO example (`examples/todo-app`): click on
"Open editor" → runtime booted → Vite 7 dev server and OpenCode 2.0.3 started → app visible
in the preview frame and chat ready. Chrome 154 headed on Xvfb on diesel2 (12 cores), driven
by `browser-control` session `bat-perf`, tab visible and focused. No chat message was sent.

At that load two stages are over their budget at the median (app visible 1,214, OpenCode
1,091); the whole open is under. Fresh, at load 4.3–4.5 (n = 5, `out/final-quiet-fresh.json`):
whole open 6,561 (6,481–6,941) before, 2,320 (2,282–3,052) now.

"Fresh" is an open with origin storage emptied (OPFS, service worker, Cache Storage,
localStorage); the browser's HTTP cache was left alone, so the 245 MB image came from the
HTTP cache or localhost. Most of the fresh-open change is another agent's work that landed
in the same period (the image is mounted while it is still arriving; see its report):
boot no longer waits for the download, and the programs then wait for image bodies
instead, which is why "spawn → app visible" is longer on a fresh open than before while the
whole open is 4.2 s shorter. This report does not separate the two contributions on fresh
opens.

## Method

```sh
bench/startup/sync.sh setup            # private copy of the worktree in target-perf/tree, everything built
bench/startup/sync.sh prepare          # after a change: bundles, toolkit, prepare, example build
bench/startup/serve.sh 4120            # the example from that copy
bun bench/startup/run.ts --label x --reopen 12 --fresh 5 [--trace] [--max-load 9]
TREE=base REF=<commit> bench/startup/sync.sh prepare && bench/startup/serve.sh 4121 base
bun bench/startup/run.ts --label ab --variants base=4121,new=4120 --reopen 12 --prime 3
bun bench/startup/native.ts --n 7      # the same two programs natively
bun bench/startup/report.ts [--steps] bench/startup/out/<file>.json
```

- **Driver** (`run.ts`): loads the page, waits 800 ms, records the click time in a capture
  listener, clicks, waits for the `bat:preview.visible` and `bat:chat.ready` marks, reads all
  marks, clicks Exit. Every time is milliseconds after the click. Each sample has the load
  average beside it. `--variants` interleaves samples of two servers (two origins, each with
  its own OPFS and its own code cache), which is the only comparison that held up on this
  machine: the load average moved between 4 and 46 during the work, and Chrome runs at
  nice 10 below the other jobs. All "before/now" numbers above are interleaved pairs.
- **Private trees**: `sync.sh` copies the worktree (or a commit, `REF=`) under
  `target-perf/`, because other agents rebuild `runtime/dist`, the toolkit and the example's
  prepared directory in place.
- **Marks**: the toolkit and the runtime host record user-timing marks (`bat:<step>`,
  `bat:boot.*` with sub-timings as `detail`), always on. With tracing on
  (`localStorage['bat-trace'] = '1'` or `bootRuntime({ trace })`) kerneld, the process
  workers and the guests post marks on a BroadcastChannel (`runtime/src/trace.ts`): worker
  attach and warm, spawn request and run, program loads, `listen`, every HTTP request and
  response of a guest server with the loader's counters. Off, a mark is one variable test.
- **Native baseline** (`native.ts`): Node 24.18 runs the guest's Vite and OpenCode from the
  same prepared tree, with `/workspace` and `/app` reproduced by bubblewrap in a private
  network namespace (so the shipped optimizer cache is valid and both use their real ports).
  Vite: spawn → ready line → document → every module of the first page fetched. OpenCode:
  spawn → ready line → the toolkit's own readiness sequence. `NODE_COMPILE_CACHE` changed
  nothing measurable (`out/native-compile-cache.json`).

### Notes on single changes

- **Start-up program modules.** `prepare({ startupModules: 'startup-modules.json' })`; the
  list is recorded by `run.ts --trace --record-modules`: 669 modules for the example's
  preview. `bat-prepare startup-program` takes ES modules and CommonJS files that begin with
  `"use strict"` (450 modules, 6.8 MB); 217 sloppy CommonJS files (0.92 MB: valibot, jiti,
  lodash, source-map-js, browserslist, semver, …) stay with `eval`; 2 are workspace files.
  The script is checked with `node --check` as a module and loaded with `import()`.
  First load of a new script: 190–290 ms; from the code cache 75–120 ms.
  `examples/todo-app/startup-modules.json` is a recording: when the dependency tree
  changes, paths that no longer exist are skipped and new modules go through `eval` until
  it is recorded again.
- **Catalog.** The server's `/api/model` response was compared byte for byte before and
  after: identical (28 models, provider `opencode`). A first attempt wrapped the global
  `fetch` for the models.dev request; with every call logged on a fresh workspace the
  wrapper was never called, and the catalog a start builds from is the one bundled in the
  server, so that code was removed. The stored models.dev row stays 5.4 MB and is parsed at
  each start before being reduced.
- **Fallback source maps.** With `optimizeDeps` source maps off (the shipped cache has
  none), Vite's `send` adds an identity map with the file as content to every JavaScript
  response that has no map. The plugin returns optimized dependencies with
  `map: { mappings: '' }`. The optimizer cache stayed valid (no re-optimization, checked
  natively).

## Tried, no gain

- **Reducing the catalog through `fetch`**: no effect, see above.
- **`NODE_COMPILE_CACHE` for the native baseline**: listening 510 against 427, readiness
  1,650 against 1,644 (n = 5); not a faster native reference.
- **Code cache from the first reopen** (a service worker storing scripts during `install`):
  not tried. Scripts loaded with `import()` from the HTTP cache get their cache on the third
  load, as the node-runtime report measured; the driver primes three opens before an A/B.
  A visitor's second and third open are therefore slower than the table (first open of a new
  program script in the traces: 190–290 ms for the 6.8 MB set, 550 ms for OpenCode's
  27.7 MB, against 75–120 and about 230).
- **Skipping the Babel pass for `react_jsx-dev-runtime.js`** (cache directory under a
  `/node_modules/` path): not done. The 122 ms the tools report attributes to it is the
  first Babel call's warm-up, which the next call would pay instead.
- **`OPENCODE_LOG_LEVEL`**: the agent writes 44 log lines by readiness; not changed.

## What is still above budget, and why

Nothing at load 3.8. At load 7 "app visible" (1,214) and "OpenCode attached" (1,091) are
over at the median. What those two consist of now (medians, `final-quiet.json`):

| Vite, after spawn | ms | | OpenCode, after spawn | ms |
| --- | --- | --- | --- | --- |
| to listening (native: 406) | 360 | | to listening (native: 1,050) | 493 |
| first render of `/` (native: 373) | 372 | | listening → health answered | 56 |
| modules, hydration, app visible | 271 | | health → plugins active (native: 213) | 357 |
| | | | plugins, config, model checks | 42 |

- **First render (372 ms)** is at the native figure. It is React Router's Babel transforms
  of the route modules, Tailwind's first scan and the render itself, in the guest's one
  thread. What would move it: transform results for unedited files computed at prepare time
  and served by a toolkit Vite plugin keyed on content hash (the tools report lists what the
  key must cover). Not built.
- **Health → plugins active (357 ms)** is OpenCode booting its per-directory services; the
  browser is 144 ms slower than native here. Not profiled inside the guest (Chrome's
  profiler was not attached to the worker); candidates are the 5.4 MB stored catalog row
  being read through the Wasm SQLite and parsed, and the three plugins being transformed at
  load (`editor-javascript.js` is 91 KB of bundled Effect).
- **OpenCode to listening (493 ms)** is half the native time because the 27.7 MB program
  comes from the code cache and starts loading before the spawn; what remains is V8 running
  the bundle's top level and 47 migration checks.
- **Listening → health (56 ms)** for a 3 ms request: not explained. The server answers
  nothing for that long after it starts listening.

## Not measured cleanly

- **Load.** Only the last runs had a quiet machine (load 3.4–4.5); everything else is
  interleaved pairs at the load stated. No run on an idle machine.
- **Per-change gains** for changes 5–7 and 9 were not isolated by their own A/B; the table
  gives step deltas and trace figures and says which.
- **Fresh opens** mix this work with the first-open agent's.
- **Second and third open** after a deploy (no code cache yet) were not measured as such.
- **A chat turn** after the catalog reduction and the start-up program: not run (messages
  cost money). Checked instead: `/api/model` identical; hot reload of an edited source file
  in the frame; Exit and Open again in the same page; a guest child process does not
  inherit `BAT_PROGRAMS` and runs (201 ms for node spawning node).
- **Memory** of two boot-time spares each holding a program script: not measured.
- **A real network.** Runtime assets other than content-addressed files are served
  `no-cache`, so each worker script costs a revalidation round trip per open; on localhost
  that is 1–2 ms and invisible here.
- Firefox and Safari: nothing was run.
