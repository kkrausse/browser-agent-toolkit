# Networking and the page-side host (2026-10-09)

What was built: the kernel HTTP/1.1 and WebSocket codecs, the page's `endpoint(port)`,
guest `net`/`http`/`https`/`fetch`, the preview service worker with its bridge worker and
WebSocket shim, and `bootRuntime`. Decisions: `docs/design/decisions.md` ("networking and
the page-side host"). ABI: `docs/design/kernel-abi.md` §15.

## Setup

- diesel2, 12 cores, headed Chrome on Xvfb through `browser-control` (session `bat-net`),
  harness server on port 4103.
- **The machine was busy the whole time** (other agents' builds and browsers). The load
  average is given beside every table; the two runs of the main table differ by 3–5× for
  that reason alone. Treat everything as an upper bound.
- Kernel wasm 330 KiB (245 KiB before the resolver; the codecs and `httparse` add ~25 KiB).
- Reproduce: `crates/bat-kernel/build.sh` (with `CARGO_TARGET_DIR=target-net`),
  `bun runtime/build.ts`, `bun runtime/src/net/harness/net-serve.ts 4103`
  (`BAT_PREPARED=<prepared dir>`), then
  - `/runtime/src/net/harness/net-test.html`: endpoint client against a raw kernel-level
    responder in a bare worker (no Node runtime);
  - `/runtime/src/net/harness/host-test.html`: boots the real runtime as the toolkit does
    (`manifest.json` → `runtime/host.js` → `bootRuntime`) and exposes `batHost` for
    scripted checks. The guest server used below is `node:http` + the `ws` package
    (8.21.3, copied into the guest unmodified).

¹ Before small bodies were sent as one buffer: every response was a transferred stream. The
right-hand column is with that change, so the two columns differ by more than load.

Against the raw kernel responder (`net-test.html`, no Node in the path), load ≈ 20:
0.18 ms median per request (0.10 min), 200 concurrent in 84 ms, 30 MB at 556 MB/s
(`Content-Length`) and 380 MB/s (chunked), WebSocket echo of 700 KB correct, first text
round trip 4.4 ms including the handshake.

So the service-worker path costs about 0.9 ms that is Chrome's (fetch event dispatch and
a synthesized response), and the runtime adds about 0.45 ms on top (two `postMessage`
hops and the kernel exchange). The page's own endpoint path is one kernel exchange.

First open, image not yet in the browser (localhost, uncompressed, 236 MB, load ≈ 20):
9.7 s to stream it into OPFS **while hashing it** (SHA-256 in `bat_node_native.wasm`),
against 1.8 s for the unhashed copy measured in the M0 notes. About 8 s of that is the
hash, i.e. ~30 MB/s; see "Open".

## What was checked in Chrome, and how

Against the raw kernel responder (`net-test.html`): `ready` resolves when the worker
listens (82 ms, the time it took to start the worker); GET, POST echo, **streamed request
body** (`ReadableStream`, sent chunked), 302 passed through unfollowed, 404, SSE delivered
event by event while 200 concurrent requests ran, 30 MB with every 4099th byte verified,
abort (`AbortError` on the reader, connection closed), `ECONNREFUSED` → `TypeError` with
the cause, WebSocket text + 700 KB binary + close handshake.

With the real runtime (`host-test.html`):

- a guest `http.createServer` answered `endpoint.fetch` (`/hello`, 100 KB POST echo);
- the **preview iframe** rendered the guest's HTML through the service worker, was
  `crossOriginIsolated`, had the shim (`__batPreviewShim`), and was controlled on its first
  navigation;
- a redirect from the guest was followed by the browser; a cookie set by the guest came
  back on the next request (service-worker jar);
- the **native `EventSource`** in the frame received 8 events at the 100 ms cadence;
- a **`ws` `WebSocketServer`** (unmodified, attached with `{ server }`) was reached from the
  frame's `new WebSocket(…, 'proto-a')`: subprotocol negotiated, `instanceof WebSocket`
  true, text echo, 300 KB binary echo, clean close 1000;
- a `hostPaths` prefix reached the real server (and carried the page origin's cookies,
  checked as a boolean only);
- **Vite 7.3.6 for the TODO app**: `vite --configLoader native --host 0.0.0.0 --port 5173
  --strictPort` listened 396–593 ms after spawn; `GET /preview/5173/` answered the
  server-rendered page in 281 ms (first request); the frame loaded it (`readyState`
  complete, 32 resources, hydrated), Vite's client logged `[vite] connected.` over the
  shimmed WebSocket, and writing `src/home.tsx` through `host.fs` changed the `<h1>` in the
  frame **68 ms** later with the window's state kept (`[vite] hot updated`). This needed
  one manual step: see "Open" (configHash).

## Open

- **Vite rejects the shipped optimizer cache in the guest** and its re-optimization does
  not finish (recorded for the tools and node-runtime agents in decisions.md). The check
  above patched `deps/_metadata.json` with the configHash computed in the guest
  (`529533e6`; shipped `82758302`). Without the patch the frame shows the server-rendered
  page and never hydrates.
- **Image hashing is slow** (~30 MB/s under load). It is paid once per image; options are
  hashing on a second worker in parallel with the write, or a SIMD build of the digest.
- **A stale readiness event** caused intermittent "socket hang up" (one benchmark run in
  three) until the kernel dropped queued events on close; three clean runs since.
- **One unexplained kernel trap and one page hang** during development (decisions.md,
  last bullet of the networking entry); not reproduced.
- The example app (`examples/todo-app`, `bun run editor`) on the real runtime: see the
  end of this file if it was reached; otherwise not run.
- Not measured: an idle machine; a real network for the image; many simultaneous
  WebSockets; request bodies larger than the socket ring through the service worker.
