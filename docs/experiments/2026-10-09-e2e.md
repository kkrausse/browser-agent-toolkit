# The TODO scenario end to end on the real runtime (2026-10-09/10)

Milestone M4: the README scenario, driven in headed Chrome (Xvfb) through `browser-control`
against `examples/todo-app` served on port 4110, with real model calls through the host
proxy. Driver: `examples/todo-app/demo/run.ts`. Decisions: `docs/design/decisions.md`
("end to end"). diesel2, 12 cores, busy the whole time (load average beside every row).

## Result

**The scenario passes: 4 of 4 consecutive runs after the last fix** (three with
`--runs 3`, then the recorded take), each from a reset workspace:

1. home: add "Record a demo GIF" and "Water the plants", tick the second, "Open editor";
   the preview shows the app (`main input#title:not(:disabled)`, both todos) and the chat is
   ready;
2. the prompt "Give this app a dark theme with a violet accent, and show how many todos are
   left under the list." is sent and the assistant finishes (6 `read`, 3–5 `edit`, 1
   `runJavascript` running `tsc --noEmit`, exit 0);
3. the preview is dark and shows "1 todo left" **in the same document** (a marker set on
   the frame's window before the prompt is still there: hot update, no reload); "Ship it"
   added inside the preview gives 2 left, ticking the first checkbox gives 1.

Earlier driver runs failed on real bugs (below), not on flakiness; none failed after the
fixes. Four runs is a small sample.

Recording: `docs/media/todo-editor-demo-rust.gif` (960 px, 12 fps, 128 colours, 1.00 MB,
28.7 s). Startup is real time; only the model's 26.9 s of work is shown at 4× and carries
the "4x" label. Made with `bun demo/run.ts --slow --record take.mp4` and
`bun demo/gif.ts take.mp4 out.gif`; the mp4 is not in git.

## Bugs found and fixes

1. **`grep` failed with "Warning: Detected unsettled top-level await".** The `rg` launcher
   awaits `WebAssembly.compile` at the top level; nothing referenced the loop while Chrome
   compiled, so the process exited 13. Fix: the four asynchronous `WebAssembly` functions
   hold a loop reference until they settle (`runtime/src/process/globals.ts`).
2. **Every esbuild-wasm call hung** (so a dependency re-optimization never finished).
   `fs.read` blocked in a kernel read; Go's Wasm runtime reads stdin with it from one
   goroutine while another writes the answer, so after the first request the whole thread
   sat in the read. Fix: `fs.read` on an fd that is not readable yet waits for readiness
   through the loop (`runtime/src/node/fs.ts`). First transform through the service 349 ms.
3. **The preview reloaded on every agent turn** (three navigations for one CSS edit).
   Tailwind's Vite plugin scans every unignored file and answers a change of a scanned
   non-module file with a full reload; OpenCode's database, config and logs are in
   `/workspace/.server`. Fix: the toolkit writes `.server/.gitignore` (`*`).
4. **After a hot update, adding a todo in the preview did not refresh the list.** An app
   bug the reloads had hidden: `root.tsx` imports the stylesheet, is hot-updated with it and
   built a new `QueryClient` each time. Fix in the example: the client is kept in
   `import.meta.hot.data`.
5. **`tsc --noEmit` in the guest stopped at TS2688** (`types: ["bun"]`): the policy pruned
   `@types/*` and `bun-types`. Fix: they stay (7 MB of 245 MB).
6. **Assistant answers with lists were unreadable** (each inline code span in its own
   narrow column): the host app styles `li` as a flex row. Fix: list layout is pinned inside
   rendered answers (`chat/styles.css`).
7. **OpenCode could die on `write EPIPE`** when a client left before its response (found by
   the Node runtime agent). Fix: such writes are dropped, as in Node (`net/http.ts`).
8. **kerneld retired a worker twice** (thread record freed twice, page spinning on a lock;
   found by the Node runtime agent, worked around there). Fix: `retire` runs once per worker.
9. **manifest.json was 6.0 MB** (optimizer cache as project files, 3.7 MB of it source
   maps) and an existing workspace never got a new cache. Fix: `derived-<sha>.json` beside
   the manifest (2.1 MB, no maps), installed only when bundle or image differs from what the
   workspace recorded, after removing the directories it owns. Manifest: 25 KB.

Also added: `bun run setup` / `bun run editor` at the repository root (`scripts/setup.ts`),
"Reset workspace" in the example (`resetWorkspace` in the toolkit and the runtime), the demo
driver and GIF builder in `examples/todo-app/demo/`.

## Still broken or untested, ranked

1. **Reliability is four runs.** No failure after the fixes, but the model's edits differ
   run to run; the driver's checks (dark background by luminance, a "N … left" text) accept
   any reasonable answer and would fail on an unreasonable one.
2. **First open of a reset workspace takes 2.3–4.8 s to chat.ready under load 6–15**
   (budget 1.5 s, for a reopen on a quiet machine). Not measured on an idle machine; that
   is M5.
3. **A re-optimization at start competes with OpenCode's boot**: in a workspace that
   imports a package outside the shipped cache, the preview became visible 7 s after its
   first response (once, load ≈ 12). It recovers by itself (Vite's "optimized dependencies
   changed. reloading").
4. **The image hash changes whenever the toolkit package is rebuilt** (the app links it as
   a workspace member, so its `dist` is in the image): a 245 MB re-download for a chat-CSS
   change. Seen three times in this session.
5. **No shell in `child_process`** and no `worker_threads.Worker` (Node runtime report): an
   agent script using `exec('a && b')` or esbuild's synchronous API fails. Not hit by the
   scenario.
6. **Hashing the image at first download** is most of the 10–14 s first boot (net report).
7. Not tried: a prompt that makes the agent install a package (no package manager in the
   guest), permission and question cards, a stopped turn (the Stop button), session
   export/import, two editors on one origin under different bases, Safari/Firefox, a real
   network, an idle machine.
8. A second tab waits 2.8 s before it is told the workspace is busy.
9. The service-worker cookie jar and `document.cookie` gap, and the unexplained kernel trap
   from the net report, were not seen and not investigated.
